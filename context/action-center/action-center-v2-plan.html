Action Center V2 build plan

What V2 does for the user, then what to build in api/ and webapp/ to get there, and the order to build it in. The tables are in action-center-v2-schema.html. The reasoning behind stored tickets, the three lanes and the fix state is in action-center-v2-solutions.html.

Repos api · webapp · db-migrations Route /action-center-v2 API prefix issue-tickets/ v1 kept, reachable Date 2026-10-26

1Objective & scope

1.1What V2 is

A new Action Center at /action-center-v2, with its own sidebar item Action Center V2. It shows what the channels (Amazon, Shopify) report as wrong, as tickets: one per product × channel × marketplace × issue type, with the parent and its affected variants inside. The system creates and clears tickets; the team moves them between three stages, assigns and snoozes them, and jumps to the right page to fix them.

1.2Ground rules

v1 stays

The /actionCenter page, its API module and its tables keep working and stay in the sidebar. V2 code never imports v1 code or reads v1 tables.

Names not tied to the page

Tables, entities, API code, queues and constants are named after the domain (tbl_issue_tickets, IssueTicket*, ISSUE_TICKET_*, issue-tickets/), so renaming the page never needs a migration. Only the webapp page layer (route, page components, store, translations) carries ActionCenterV2.

External only

A ticket exists only if the channel reports the problem. The one exception is the stock rule, which mirrors the Command Center exactly (warehouse quantity when mapped).

No leftovers

Anything V2 replaces outside v1 (the Command Center redirect mapping, the product-page v1 trigger mount) is removed in the same step, not left for later (§6).

1.3End-to-end flow

channel state changes (publish result, import, notification, health, sweep …)
      │
      ▼
 IssueTicketTriggerService.enqueue(scope)  debounced, merged per account × channel × market
      │  queue ISSUE_TICKET_EVALUATION (api-worker)
      ▼

      │
      ▼
 /action-center-v2  top bar · 3 lanes · ticket dialog · right-edge drawer
      │  primary action (e.g. Open Price) → TODO → IN_PROGRESS, self-assign
      ▼

      │  user fixes in Categra → fix state "Set in Categra · not published" → the tab's own Publish
      ▼

3.8Right-edge drawer (V2 page)

A trigger stuck to the center-right of the page, styled like the product page's Product Action Context trigger, opens a drawer with:

  • Category breakdown: a ring by group and a list of issue types with count, % and bar, for the current board filters (excluding the issue type filter itself). Clicking an issue type sets it as the issue type filter; clicking it again clears it.
  • Recent activity: the 5 latest events of the last 7 days in the board's channel / market / issue type scope (the deploy seed writes no events, so it adds nothing here) ("Priya moved Linen Shirt to In progress", "System cleared Desk Lamp · Main image", "Wool Beanie re-appeared"). "See all" opens a paginated list. Clicking an event opens the ticket dialog if the ticket still exists, else shows "Resolved".

3.9Product page drawer (V2)

Replaces the v1 trigger on /products/[product]. Same placement (center-right edge), shaped like the V2 board:

  • Trigger: counts by priority (Red / Yellow / Blue) for this product's open tickets. Hidden when there are none.
  • Drawer: this product's tickets across channels and markets, grouped by channel · market, in board order. Each ticket is a compact card: issue type, fix state, affected variants (expandable list with SKU/ASIN and fix state per variant), stage, assignee, primary action, ⋮ (Move to, Snooze for me).
  • The primary action switches the product page tab (same rules as §3.7) and closes the drawer.
  • It opens only from its trigger. It never auto-opens from URL params.
  • Kept from v1, refined: grouping by scope, the per-variant list, "Publishing…" state with a link to the task manager. Dropped: inline stock/price editing, the remediation banner with skip/next, supporting/technical sections, the three counters (actions/signals/sync).

Snoozed tickets in the product drawer

The drawer hides the caller's snoozed tickets by default, so a snoozed ticket neither lists nor counts in the trigger badge. The drawer says how many it is hiding and lets the user reveal them. "Scope" is this product across the channels and markets the caller can see.

  • Footer strip: when the scope has snoozed tickets, a quiet one-line strip sits under the last group: "2 snoozed tickets hidden" with a text button Show. With none, nothing renders. When there are no open tickets and only snoozed ones, the empty state reads "No open tickets · 2 snoozed" with the same Show button.
  • After Show: the snoozed tickets join the list in board order, each with a muted "Snoozed until 14 Nov" chip and the ⋮ item Unsnooze in place of Snooze for me. The strip turns into Hide snoozed. The choice lasts for this drawer session only and resets to hidden on close.
  • Trigger badge: unchanged by Show. It counts unsnoozed tickets only (priorityCounts is computed in SQL over all of them, not over the first 200 cards).
  • Unsnoozing inside the drawer updates the card in place, drops the strip count by one and raises the badge.
  • API: POST products/:productId/tickets takes { includeSnoozed?: boolean } and returns { cards, hasMore, priorityCounts, snoozedCount }. snoozedCount is the caller's own snoozed tickets of the product; hasMore is true past the 200-card cap.

4.2Detectors (shared with the Command Center)

Counts must match the CC, so detection must not be a second copy of its rules.

  • Refactor in the CC (no behaviour change): split buildAttentionItems in attention.builder.ts into a per-unit classifier (one row per variant/product × channel × marketplace with its family and sub type) and the existing aggregation into cards. These are CC functions, so they keep CC names.
  • SQL scope options: the pulse / attention SQL builders (buildInventoryKeysQuery, buildPricingKeysQuery, buildListingIssuesQuery, buildAttentionKeySignalsQuery, buildBuyBoxAttentionQuery) get an optional productIds filter and an uncapped mode. The CC keeps its LISTINGS_MAX_ISSUES_SCANNED cap; the evaluator can't cap, or tickets would be silently missing.
  • Channel-level families come from ChannelHealthService.getHealth, as in the CC.
  • issue-ticket-detectors.ts folds the per-unit rows into ticket drafts: variants under their parent product, one draft per key, items = (variant, sub type), plus the blocker-hides-warning rule per product × marketplace.
  • One item per (variant, sub type): the detector dedupes before the diff. Channel health emits METRIC_BAD once per bad metric and POLICY_BAD once per policy (channel-health.derivation.ts), so two bad metrics on one marketplace would otherwise produce two (NULL, METRIC_BAD) items and break UNIQUE (ticket_id, variant_id, sub_issue_type) NULLS NOT DISTINCT. Which metrics / policies are bad is evidence, read live in the dialog.
  • Verification: for an account, the sum of affected units over the drafts per family equals the CC card counts (uncapped). This check is part of step 3 in §8.

4.3Evaluator & queue

  • Queue ISSUE_TICKET_EVALUATION (GlobalEnums.QueueNames), registered in the queue config map and the worker list like READINESS_RECALCULATION. Processor IssueTicketEvaluationProcessor extends BaseQueueProcessor.
  • Job payload: { accountId, channelId, amazonMarketplaceIds?, productIds?, issueTypes?, sources[] }.
  • IssueTicketEvaluatorService.evaluateScope(scope): run the detectors for the scope → load the stored tickets of exactly that scope → diff and write in one transaction under pg_advisory_xact_lock(accountId, channelId) → write events. The rules are in schema §5 and solutions §1.6.
  • ITEMS_CHANGED is written when the affected count changes or the set of sub types changes. A channel-level ticket keeps a count of 0, so without the second rule C1 going from ACCOUNT_AT_RISK to ACCOUNT_DEACTIVATED would leave no history entry. For a sub-type change, from_value / to_value hold the sorted sub-type sets.
  • Awaiting channel → In progress (the evaluator's only status move) happens only when (a) the evaluation's sources include the publish kind that fixes the ticket's issue type (PRICE_PUBLISH for price issues, STOCK_PUBLISH for stock, FS_RESULT for listing, media and product-type issues), (b) none of the ticket's items is still PUBLISHING, and (c) the issue is still reported. Otherwise an unrelated attribute publish returning first would bounce a price ticket whose price push is still running. The write is conditional, UPDATE … SET status = 'IN_PROGRESS' WHERE id = :id AND status = 'AWAITING_CHANNEL', so it never overwrites a move a user made a moment earlier.
  • It skips product-level families of a channel that has an open CONNECTION ticket (stale external state), and evaluates the whole channel when the connection comes back.

4.4Trigger hook points

IssueTicketTriggerService.enqueue(scope, source) never throws (same contract as ReadinessTriggerService.trigger). It debounces with ISSUE_TICKET_EVALUATION_DEBOUNCE_MS and must never drop product ids:

  • Time bucket in the job id: account:channel:markets:issueTypes:bucket, with bucket = floor(now / debounce), as readiness-trigger.service.ts does. A trigger that arrives while a job is already active lands in the next bucket's job instead of being ignored by BullMQ's duplicate-id check.
  • Atomic merge while delayed: product ids for a bucket go into a Redis set keyed by the job id (SADD), and the job carries only that key. The processor reads and deletes the set when it starts (SMEMBERS + DEL in one MULTI), so ids added up to that moment are included and later ones fall into the next bucket. No get-then-update on job data.

Product / variant delete: synchronous clear (not queued)

A queued evaluation would run after the delete has committed, when the FK cascade has already removed the tickets silently. So the product and variant delete paths call IssueTicketEvaluatorService.clearScope(scope, tx) inside the delete transaction, before the delete. It writes CLEARED events (source SCOPE_REMOVED), deletes the product's tickets, and for a variant delete removes that variant's items and recounts affected_variant_count on the tickets it touched, deleting a ticket left with no items (also CLEARED). The FK cascades stay only as a backstop for a delete path that doesn't call it.

Publish-start hook (not an evaluation)

IssueTicketPublishHookService.onPublishStarted(scope, kind, userId) runs synchronously, never throws, and doesn't re-detect anything. It is called where a publish is started: forward sync task creation (Channels tab), price publish (Pricing tab, and price auto publish) and stock Save & Publish (Stock tab). It moves TODO / IN_PROGRESS tickets in that product × channel × markets scope to AWAITING_CHANNEL when the publish kind fixes their issue type (price → price issues, stock → stock issues, forward sync → listing, media and product-type issues) and at least one of their items has a fix state other than NOT_FIXED (READY_TO_PUBLISH or PUBLISHING). Accepting PUBLISHING matters: the publish flow may set sync_in_progress before the hook runs, and the items then already read as publishing. It writes STATUS_CHANGED with source PUBLISH_STARTED; the actor is the user who clicked, or NULL (system) for auto publish. Tickets the publish doesn't fix (e.g. BUY_BOX_LOST on a price push) stay where they are. The result is still evaluated by the matching source above.

4.5Cron jobs (cron.service.ts)

  • Nightly sweep: enqueue a full evaluation per channel, accounts staggered over ISSUE_TICKET_SWEEP_WINDOW_MINUTES.
  • Daily: delete expired snoozes; delete events past ISSUE_TICKET_EVENT_RETENTION_DAYS in batches.
  • Seed: a script (api/scripts/) that runs the sweep once for all accounts on deploy, with source SEED: tickets and items only, no events, so recent activity starts empty instead of listing every pre-existing issue as "created".

4.6Fix state

IssueTicketFixStateService.resolveFixStates(items) computes NOT_FIXED | READY_TO_PUBLISH | PUBLISHING | NOT_APPLICABLE for a page of items at read time, using the rules in solutions §3.4: price / media baselines (tbl_price_sync_baselines, tbl_product_media_sync_baselines), the warehouse quantity for stock, unpublished changes for listing issues, and sync_in_progress on PCM / VM / PC / PVC. It is also the basis of the Fix state filter.

4.7Primary actions

ISSUE_TICKET_PRIMARY_ACTIONS maps each issue type to an action kind. The API returns { kind, label, destination }, and both follow the fix state: NOT_FIXED → the fix destination; READY_TO_PUBLISH → Review & publish to the tab that owns that publish; PUBLISHING → Publishing…, a link to the task manager. The board never publishes; the destination page's own controls do, with their existing sync locks, unsaved-change checks, trial limits and sockets.

PATCH tickets/:ticketKey/assignee Assign / unassign / assign to me.
PUT · DELETE tickets/:ticketKey/snooze Snooze / unsnooze for the caller.
POST tickets/:ticketKey/primary-action The system move + self-assign; returns the destination.
GET assignees?channelId= Assignable team members for a channel.
POST insights/breakdown Counts by group / issue type for the filters.
POST insights/activity Recent activity, paginated.
POST products/:productId/tickets Product drawer: the product's tickets across channels, plus counts by priority for the trigger.

Mutations address tickets by key inside the caller's account and return the updated card. A cleared ticket returns 404 TICKET_CLEARED. JSDoc on every function, one short line (api CLAUDE.md).

4.9Permissions & assignees

  • Read endpoints: actionCenter.view or actionCenter.* (or owner / admin), and the ticket's channel must be in the user's channels (ChannelService.getUserWiseChannels).
  • Assigning others: actionCenter.assign. "Assign to me", moving and snoozing: view access.
  • Candidates: active members of the account who have Action Center access and access to the ticket's channel (role channels / user channels). Fresh code in issue-ticket-assignees.service.ts; v1's getActionCenterAssigneeCandidates isn't imported.
  • At read time an assignee who lost access is shown as unassigned.

4.10Issue-type order & priority

Neither is stored on the ticket. issue-ticket-taxonomy.ts exposes resolveIssueTypeOrder(accountId) and resolveIssuePriority(issueType), reading COMMAND_CENTER_ATTENTION_FAMILY_ORDER / COMMAND_CENTER_ATTENTION_SEVERITY today. Every reader goes through it:

  • Lane query: ORDER BY array_position(:issueTypeOrder, issue_type), … (schema §6.1).
  • Priority filter: expanded to issue_type = ANY(:issueTypesOfThatPriority).
  • Priority facets, product drawer "3 Red · 1 Yellow", card stripe, dialog header, CSV: GROUP BY issue_type or per row, mapped by the resolver.

A per-account order later changes only the resolver; no ticket row is rewritten.

7.2Risks

Risk Mitigation
A pipeline that changes external state doesn't enqueue an evaluation Nightly sweep; last_evaluated_at lets us find stale scopes; trigger coverage table (§4.4) is checked off in step 5.
CC refactor changes CC counts Step 2 compares CC output before and after on a real account.
Uncapped detector SQL is slow on large accounts Product-scoped runs for events; the full run only in the sweep, staggered.
