Action Center V2 schema

The four new tables behind Action Center V2: one row per open ticket, its variant items, per-user snoozes and an audit trail. It follows the decisions in action-center-v2-solutions.html, with the 2026-10-23 answers applied. The v1 tables are not used or changed.

Repo db-migrations · api/entities Tables 4 new, 0 changed Companion action-center-v2-plan.html Date 2026-10-26

1Objective & naming

A ticket is a stored record of an open issue reported by the channel. It is created, updated and deleted by the system, and only its stage, assignee and snoozes are owned by users.

1.1What the schema must do

Requirement (brief) How the schema answers it
One ticket = product × channel × marketplace × issue type, parent and variants inside One tickets row per key. Variants are rows in ticket_items.
Universal id, irrelevant keys = 0 Real FK key columns, NULL when a key doesn't apply, plus a generated ticket_key that writes COALESCE(col, 0), so the external id still shows 0 (§4.1).
Main table manages per-item status; cleared = deleted tickets.status has no "cleared" value. Clearance is a DELETE with cascade.
Separate per-user snooze table ticket_snoozes, unique per ticket × user.
Separate audit table (status, cleared, re-generated…) ticket_events, keyed by ticket_key with no FK, so it outlives the ticket.
Red / Yellow / Blue priority, as in the Command Center Not stored. The API derives it from issue_type through the CC severity constant (§4.2), so it can't drift.
Sort: issue type → variants DESC → product → channel → marketplace; items by variant Issue-type order resolved by the API and passed into the query (array_position, §6.1), so it can become dynamic without rewriting rows; stored affected_variant_count for the second key.
Recent activity in the right-edge drawer Events carry denormalised scope columns, so they can be filtered after the ticket is gone (§3.4).

1.2Naming rules

  • Names are not tied to the page. Tables, entities, enums and constants are named after what they hold, not after Action Center, so a page rename never needs a migration: tbl_issue_tickets, entity IssueTicket, enum IssueTicketStatus, constants ISSUE_TICKET_*. No V2 either.
  • No name clashes with v1: v1 uses tbl_action_center_issue_workflows, _issue_assignments, _lifecycle_events. Every new table starts with tbl_issue_ticket, and index names use idx_issue_ticket* / uq_issue_ticket*.
  • Only the webapp page layer (route, page components, store, translations) carries ActionCenterV2, as the companion plan describes.
  • Columns are snake_case, including created_at / updated_at, like the recent tables (tbl_llm_failures). Entities map them with createdAt: 'created_at', updatedAt: 'updated_at'.

2.2Write flow

external event  (publish result · import · stock/price publish · notification · health · sweep)
     │
     ▼
 evaluator (worker, one transaction, advisory lock on account × channel)
     ├─ new key            → INSERT tickets + items   → events CREATED | REAPPEARED
     ├─ key still present  → replace items, update counts → events ITEMS_CHANGED (count or sub-type set changed)
     │                       + AWAITING_CHANNEL → IN_PROGRESS only on the fixing publish kind's result,
     │                         nothing still PUBLISHING, conditional UPDATE   → STATUS_CHANGED
     └─ key gone           → DELETE tickets (items + snoozes cascade) → events CLEARED

 publish start (FS task created · price publish incl. auto · stock publish)
     └─ TODO / IN_PROGRESS tickets in scope, items not NOT_FIXED → tickets.status AWAITING_CHANNEL → STATUS_CHANGED (PUBLISH_STARTED)

 product / variant delete (same transaction, before the DELETE)
     └─ clearScope → events CLEARED (SCOPE_REMOVED) → DELETE tickets / items + recount (FK cascade = backstop only)

 user (API, one transaction per mutation)
     ├─ move stage / primary action           → tickets.status          → STATUS_CHANGED
     ├─ assign / unassign                     → tickets.assignee_*      → ASSIGNEE_CHANGED
     └─ snooze / unsnooze                     → ticket_snoozes          (not audited)

 cron
     ├─ expired snoozes  → DELETE
     └─ events older than retention → DELETE

3Tables

Column lists are final for the first migration. Types use Postgres names. "Sys" = written by the evaluator only.

3.1tbl_issue_tickets

Column Type Null / default Writer Notes
id bigserial PK — Internal only. The API and URLs use ticket_key.
account_id bigint NOT NULL Sys FK tbl_accounts(id) ON DELETE CASCADE.
product_id bigint NULL Sys Parent or standalone product. NULL for channel-level tickets. FK tbl_products(id) ON DELETE CASCADE as a backstop only: product delete / unlist still clears through the evaluator first, so CLEARED is audited (§7).
channel_id bigint NOT NULL Sys FK tbl_channels(id) ON DELETE CASCADE. Every issue type is at least channel-scoped.
amazon_marketplace_id bigint NULL Sys NULL for Shopify and for channel-level Amazon tickets. FK tbl_amazon_marketplaces(id) ON DELETE CASCADE. It is a lookup table and rows are normally never deleted (deactivation is a flag), but if one is, its tickets are meaningless and must not block the delete.
issue_type varchar(64) NOT NULL Sys CC attention family (§4.2). Validated in the app, not by a CHECK, so new families need no migration.
ticket_key varchar(255) GENERATED ALWAYS … STORED DB 'productId:' || COALESCE(product_id, 0)::text || '||channelId:' || channel_id::text || '||amazonMarketplaceId:' || COALESCE(amazon_marketplace_id, 0)::text || '||issueType:' || issue_type. COALESCE keeps the key's 0 segments and is immutable, so it is allowed here. The explicit ::text casts are required: text || bigint is only STABLE and Postgres rejects it in a generated column. The column is never NULL, so the plain unique index on it enforces identity.
affected_variant_count integer NOT NULL DEFAULT 0 Sys Distinct non-null variant_id among the items. 1 for a standalone product, 0 for channel-level tickets. Second sort key.
status varchar(24) NOT NULL DEFAULT 'TODO', CHECK IN ('TODO','IN_PROGRESS','AWAITING_CHANNEL') User + system moves The lane. There is no CLEARED value.
status_changed_at timestamptz NOT NULL DEFAULT NOW() User + system moves "In this stage for 3 d" on every card. Kept on the row because events are deleted after 180 days, and a "stuck in stage" sort or filter needs it here.
assignee_user_id bigint NULL User / primary action FK tbl_users(id) ON DELETE SET NULL. One owner per ticket. Who assigned it and when live in the ASSIGNEE_CHANGED event (actor, occurred_at).
last_evaluated_at timestamptz NOT NULL DEFAULT NOW() Sys Set on every evaluation that covered this ticket. Lets the sweep find stale scopes.
created_at, updated_at timestamptz NOT NULL DEFAULT NOW() — created_at is when this occurrence was first seen: the evaluator inserts the row on first detection, and a re-appearance is a new row. The CSV "detected at" reads it.

3.1.1Constraints & indexes

Name Definition Serves
uq_issue_tickets_account_key UNIQUE (account_id, ticket_key) Identity; every lookup by key (dialog, mutations, deep links).
idx_issue_tickets_lane (account_id, status) Lane rows and lane counts. The order (§6.1) starts with the API-resolved issue-type order, so it is a top-N sort over the lane's rows, not an index-ordered scan; at ~50 k tickets per account (§9) that is the same scale as the counts query.
idx_issue_tickets_scope (account_id, channel_id, amazon_marketplace_id, issue_type) Evaluator scope load (§6.6), channel / market / issue type filters, counts.
idx_issue_tickets_product (account_id, product_id) WHERE product_id IS NOT NULL Product page drawer, product-scoped evaluations, product delete clearing.
idx_issue_tickets_product_fk (product_id) WHERE product_id IS NOT NULL The FK cascade's DELETE … WHERE product_id = $1, which has no account_id. Without it a bulk product delete scans the table per product.
idx_issue_tickets_assignee (account_id, assignee_user_id) WHERE assignee_user_id IS NOT NULL Assignee filter.
Why the key columns and not a free-form key

The four key columns are the source of truth and are what filters and the diff use. ticket_key is derived from them by the database, so the external id can never drift from the columns.

3.2tbl_issue_ticket_items

Column Type Null / default Notes
id bigserial PK
ticket_id bigint NOT NULL FK tbl_issue_tickets(id) ON DELETE CASCADE.
variant_id bigint NULL NULL = parent / standalone product, or a channel-level item. FK tbl_product_variants(id) ON DELETE CASCADE as a backstop: a cascaded item doesn't update the ticket's count, so variant delete still re-evaluates through the evaluator (§7).
sub_issue_type varchar(64) NOT NULL §4.2, e.g. NO_PRICE, UNSUPPORTED_FORMAT, CONNECTION_LOST, a listing bucket.
created_at timestamptz NOT NULL DEFAULT NOW() When this (variant, sub type) was first seen, as on the ticket. Set on insert and never updated: it is kept while the item survives re-evaluations, and is later than the ticket's created_at when a variant joins an existing ticket, so the dialog can show "since 2 d" per variant.
  • uq_issue_ticket_items UNIQUE (ticket_id, variant_id, sub_issue_type) NULLS NOT DISTINCT, so two parent-level rows with the same sub type collide (same pattern as uq_trv_scope on tbl_readiness_values; Postgres 15+). It keeps plain ON CONFLICT (cols) working, with no COALESCE expression index, and serves the item order (variant_id ASC NULLS FIRST, then sub_issue_type).
  • idx_issue_ticket_items_variant (variant_id) WHERE variant_id IS NOT NULL, for search, variant deletion clearing and the FK cascade.
  • The detector emits one item per (variant, sub type). Some sources repeat a sub type with different details, e.g. channel health emits METRIC_BAD once per bad metric; those collapse into one item, and which metrics are bad is evidence read live in the dialog.
  • No evidence is copied here (prices, ASINs, error text, image URLs). The dialog reads it live, and the fix state (Not set / Set, not published / Publishing) is computed when read. Neither can go stale here.
  • No updated_at: an item is inserted or deleted, never edited. Updates to a ticket's items are a set diff (delete gone, insert new, keep the rest).

3.3tbl_issue_ticket_snoozes

Column Type Null / default Notes
id bigserial PK
ticket_id bigint NOT NULL FK tickets ON DELETE CASCADE. A cleared ticket takes its snoozes with it, so a re-appearance is not snoozed.
user_id bigint NOT NULL FK tbl_users(id) ON DELETE CASCADE.
snoozed_until timestamptz NOT NULL From the Details-tab date picker (DatePickerDialog). The API rejects past dates.
created_at, updated_at timestamptz NOT NULL DEFAULT NOW() Re-snoozing updates the row.
  • uq_issue_ticket_snoozes UNIQUE (ticket_id, user_id). It serves the per-ticket EXISTS in the lane query.
  • idx_issue_ticket_snoozes_until (snoozed_until), for the cleanup cron.
  • Reads treat snoozed_until <= NOW() as not snoozed, so an expired row that the cron hasn't deleted yet is harmless. Read paths never write.
  • Snoozes are personal, so they are not audited (they would make the shared activity feed noisy).

3.4tbl_issue_ticket_events

Column Type Null / default Notes
id bigserial PK
account_id bigint NOT NULL FK tbl_accounts(id) ON DELETE CASCADE.
ticket_key varchar(255) NOT NULL No FK. It links every occurrence of the same key: CREATED → CLEARED → REAPPEARED → …
product_id, channel_id, amazon_marketplace_id bigint channel_id NOT NULL; the other two NULL Copies of the key columns (NULL where the ticket's column is NULL), so the activity feed can be filtered by channel, market and product after the ticket row is deleted. No FKs: a cascade would wipe a deleted product's or channel's history, and the history must stay readable for the account.
issue_type varchar(64) NOT NULL Copy, for the issue type filter and the label.
event_type varchar(24) NOT NULL, CHECK (§4.3)
from_value, to_value varchar(64) NULL STATUS_CHANGED: statuses. ASSIGNEE_CHANGED: user ids (null = unassigned). ITEMS_CHANGED: affected counts, or for a sub-type change with the same count the sorted sub-type set (e.g. ACCOUNT_AT_RISK → ACCOUNT_DEACTIVATED). CREATED / REAPPEARED: to_value = affected count. CLEARED: from_value = the status it was cleared from.
actor_user_id bigint NULL FK tbl_users(id) ON DELETE SET NULL. NULL = system.
source varchar(32) NOT NULL §4.3. App-validated.
occurred_at timestamptz NOT NULL DEFAULT NOW()
  • idx_issue_ticket_events_key (account_id, ticket_key, occurred_at DESC): the dialog history and the REAPPEARED check.
  • idx_issue_ticket_events_feed (account_id, occurred_at DESC): recent activity, with the channel / market / issue type filters applied on the rows.
  • idx_issue_ticket_events_retention (occurred_at): the retention cron.
  • Append-only. No updated_at.

4Keys & value sets

4.1Ticket key & item key

productId:12||channelId:4||amazonMarketplaceId:2||issueType:MISSING_PRICE
productId:12||channelId:4||amazonMarketplaceId:2||issueType:MAIN_IMAGE||variantId:55||subIssueType:UNSUPPORTED_FORMAT
Rule Detail
Fixed segments, fixed order Every ticket has all four segments. A segment that doesn't apply is 0 in the key and NULL in its column. Shopify → amazonMarketplaceId:0. Channel-level → productId:0. The parser maps 0 back to NULL before querying (IS NULL, not = 0).
Account is not in the key Uniqueness is (account_id, ticket_key). The API always resolves keys inside the caller's account.
Item key The ticket key + ||variantId: + ||subIssueType:, with a NULL variant_id written as 0. Built by the API (not stored), used in the dialog, CSV rows and the destination-page highlight.
Parsing One shared parser in the API (parseIssueTicketKey) and one in the webapp. Split on ||, then on the first :. Reject unknown segment names, missing segments and non-numeric ids (400).
URL use The key is URL-safe with encodeURIComponent (| → %7C). Path params use the encoded form.

4.2Issue taxonomy

Three levels, as the brief asks ("main issue type, then the actual sub issue"): the group is the CC step, the issue type is the CC family (stored on the ticket), and the sub issue type is stored on each item. Only the issue type and sub issue type are stored; the group comes from a constant map.

Rank and priority come from the Command Center constants

The rank and priority above are illustrative and are not stored. One API resolver reads COMMAND_CENTER_ATTENTION_FAMILY_ORDER and COMMAND_CENTER_ATTENTION_SEVERITY (resolveIssueTypeOrder(accountId), resolveIssuePriority(issueType)) for the lane order, card stripe, priority filter, facets, product drawer and CSV. If the order becomes a per-account setting, only the resolver changes; no ticket row is rewritten. Priority would become a stored, evaluator-written column only if it ever varied within one issue type.

  • Stock rule (decision 2026-10-23): OUT_OF_STOCK / LOW_STOCK / STOCK_SYNC use exactly the Command Center classifier: warehouse quantity for mapped non-FBA listings, otherwise the remote quantity. This is the one deliberate exception to "external only", so the counts on both pages match.
  • Mutually exclusive stock types: an item is in at most one of out of stock → low stock → stock sync (the CC rule).
  • Blocker hides warning: a product × marketplace with an AMAZON_LISTING_BLOCKER ticket gets no AMAZON_LISTING_WARNING ticket.

4.3Status, priority, events, sources

status (CHECK)

TODO · IN_PROGRESS · AWAITING_CHANNEL

priority (derived, not a column)

RED · YELLOW · BLUE, from the issue type (§4.2)

event_type (CHECK)

CREATED · REAPPEARED · ITEMS_CHANGED · STATUS_CHANGED · ASSIGNEE_CHANGED · CLEARED

source (app-validated)

USER · PRIMARY_ACTION · PUBLISH_STARTED · FS_RESULT · BS_IMPORT · STOCK_PUBLISH · PRICE_PUBLISH · AMAZON_NOTIFICATION · SHOPIFY_WEBHOOK · BUY_BOX_REFRESH · CHANNEL_HEALTH · DATA_SYNC · PRODUCT_TYPE_CHANGE · SCOPE_REMOVED · SWEEP · SEED

PRIMARY_ACTION and PUBLISH_STARTED are the system moves caused by a user click: the actor is the user who clicked (the primary action on the board, or Publish on the product page) and the source names the move. A PUBLISH_STARTED move from price auto publish has no click, so its actor is NULL. Every other non-USER source has actor_user_id = NULL. SEED (first deploy) writes tickets and items but no events, so recent activity doesn't start with every pre-existing issue listed as created.

5Ownership & lifecycle

5.1Who writes which column

Writer May write Never writes
Evaluator Insert / delete tickets; key columns; affected_variant_count, last_evaluated_at; items; events with a system source. One move: AWAITING_CHANNEL → IN_PROGRESS, only when the evaluation's sources include the publish kind that fixes that issue type (PRICE_PUBLISH / STOCK_PUBLISH / FS_RESULT), no item is still PUBLISHING, and the issue is still reported. Written as a conditional UPDATE … WHERE status = 'AWAITING_CHANNEL'. Assignee column, snoozes, any other status move.
Publish-start hook One move: TODO / IN_PROGRESS → AWAITING_CHANNEL for tickets in the published scope whose issue type that publish kind fixes and whose items are not NOT_FIXED (READY_TO_PUBLISH or PUBLISHING, as sync_in_progress may already be set); status_changed_at; STATUS_CHANGED with source PUBLISH_STARTED, actor = the publishing user (NULL for price auto publish). Anything else; tickets the publish doesn't fix.
Delete path (clearScope) In the product / variant delete transaction, before the delete: CLEARED events (source SCOPE_REMOVED), delete the product's tickets or the variant's items, recount affected_variant_count, delete a ticket left with no items. Status, assignee, snoozes of surviving tickets.
User mutations status + status_changed_at; assignee_user_id; own snooze rows; events with source USER / PRIMARY_ACTION. Insert or delete tickets, items, system columns.
Cron Delete expired snoozes; delete events past retention. Tickets.

5.2Lifecycle walk-through

Product 12, Amazon channel 4, DE (2), 4 variants, 3 of them have no price on Amazon.

# What happens tickets items events
1 BS import evaluates the scope INSERT status TODO, count 3 (shown Red: MISSING_PRICE) variants 51, 52, 53 · NO_PRICE CREATED, to 3, source BS_IMPORT
2 Priya clicks Open Price status IN_PROGRESS, assignee Priya — STATUS_CHANGED TODO→IN_PROGRESS, ASSIGNEE_CHANGED null→Priya, actor Priya, source PRIMARY_ACTION

On re-appearance the previous assignee is not restored (decision §5 #6). The dialog history shows who owned it before.

6Read queries

The query shapes the schema is indexed for. Exact SQL is written per section during the build.

6.1Lane page

SELECT t.*
FROM tbl_issue_tickets t
WHERE t.account_id = :accountId
  AND t.status = :status
  AND t.channel_id = ANY(:allowedChannelIds)            -- user's channel access
  -- optional filters: channel, issue types, assignee (incl. unassigned);
  -- marketplace: AND (t.amazon_marketplace_id = :m OR t.amazon_marketplace_id IS NULL)  -- keeps channel-wide tickets
  -- a priority filter is expanded by the API to issue_type = ANY(:issueTypesOfThatPriority)
  AND NOT EXISTS (                                        -- hide my active snoozes
        SELECT 1 FROM tbl_issue_ticket_snoozes s
        WHERE s.ticket_id = t.id AND s.user_id = :userId AND s.snoozed_until > NOW())
ORDER BY array_position(:issueTypeOrder, t.issue_type),       -- API-resolved order, e.g. '{CONNECTION,ACCOUNT_HEALTH,…}'
         t.affected_variant_count DESC, t.product_id NULLS FIRST, t.channel_id, t.amazon_marketplace_id NULLS FIRST
LIMIT :limit OFFSET :offset
  • The Snoozed filter turns NOT EXISTS into EXISTS (only my snoozed tickets).
  • The page is then enriched with one query per concern for the visible ids only: product name / image / SKU, assignee name / avatar, item summary, and the fix state per item (baselines + sync_in_progress flags).
  • A Fix state filter (e.g. "Set in Categra · not published") is an extra EXISTS on the items joined to the baseline tables. It is the only filter that touches non-ticket tables, so it is applied after the indexed filters.

6.2Counts & facets

SELECT status, COUNT(*) AS tickets, SUM(GREATEST(affected_variant_count, 1)) AS items
FROM tbl_issue_tickets t
WHERE /* same filters + snooze rule as 6.1 */
GROUP BY status

The filter dialog's facet counts (per issue type, channel, market, assignee) use the same WHERE grouped by that column. Priority facets and the product drawer's "3 Red · 1 Yellow" group by issue_type and the API sums the groups per priority. The "N tickets · M items" header after a Command Center hand-off reads from this query.

6.3Search

Searches product name, variant name, product / variant SKU and ASIN. It is an EXISTS over two branches, so a ticket matches on its parent or any of its items:

  • Parent: tbl_products (name in base language, SKU) and the product's Amazon listing ASIN (tbl_product_channel_marketplaces).
  • Items: tbl_product_variants (name, SKU) and the variant ASIN (tbl_variant_marketplaces) for variant_id IS NOT NULL.

Matching is ILIKE on the joined values, like the v1 and products-list search. Channel-level tickets (product_id IS NULL) never match a search.

6.4Ticket dialog

  1. Ticket by (account_id, ticket_key). Not found → 404 TICKET_CLEARED.
  2. Items ordered by variant_id NULLS FIRST, sub_issue_type (parent row first), joined to the variant name / SKU / ASIN.
  3. Live evidence per item from the issue type's source tables (price baseline vs live price, remote vs warehouse stock, channel errors, Buy Box status…).
  4. History: ticket_events by key, newest first. It spans earlier occurrences too.

6.5Breakdown & recent activity

  • Category breakdown (right-edge drawer): the counts query grouped by issue_type, rolled up to groups with the constant map. It uses the board's current filters (excluding the issue type filter itself, so the breakdown can switch between types).
  • Recent activity: ticket_events for the account in the last ISSUE_TICKET_RECENT_ACTIVITY_DAYS, filtered by the board's channel / market / issue type on the copied columns (market again includes NULL, channel-wide rows), plus the caller's channel access. Newest first, 5 in the drawer and a paginated "See all". The deploy seed writes no events, so it never appears here.

7Retention & maintenance

Job Schedule Statement
Expired snoozes Daily DELETE FROM tbl_issue_ticket_snoozes WHERE snoozed_until <= NOW()
Event retention Daily DELETE … ticket_events WHERE occurred_at < NOW() - ISSUE_TICKET_EVENT_RETENTION_DAYS, in batches of 10 000.
Nightly sweep Nightly, staggered per account Full evaluation of every channel. It writes tickets, not maintenance, but it is the safety net for drift.

Clearing on scope removal uses source SCOPE_REMOVED. Product and variant deletes call clearScope synchronously, inside the delete transaction and before the delete, so a CLEARED event is written and ticket counts stay right; a queued evaluation would run after the commit, when the cascade had already removed the rows. Unlisting and marketplace deactivation delete no rows, so they go through the normal queued evaluation. The product_id / variant_id FK cascades are only a backstop for a delete path that doesn't call clearScope: they remove rows silently (no CLEARED event, and a cascaded item leaves the ticket's affected_variant_count stale, possibly with zero items). The nightly sweep corrects what a cascade leaves behind. Channel deletion is the FK cascade on channel_id; its events stay, since events have no FKs.

9Scale notes

  • Volume: one ticket per product × channel × marketplace × type, not per variant. A 50 000-product account across 2 channels and 5 markets with 10 % of listings affected is roughly 50 k tickets and a few hundred k items. Plain B-tree indexes are enough; no partitioning.
  • Read cost is an indexed range scan of the lane ((account_id, status)), a top-N sort for the API-resolved issue-type order, and enrichment of one page (≤ 30 ids). The sort reads the same rows the counts query already reads. There is no snapshot build and no cache.
  • Write cost is set-based per scope: one detector pass, one diff, bulk insert / delete. Debounce + merged product ids keep a 5 000-product import to a handful of evaluations.
  • Concurrency: pg_advisory_xact_lock(account_id, channel_id) serialises evaluations of one channel. User mutations lock only their row (UPDATE … WHERE id). The evaluator never writes the assignee or snoozes; its one status write (Awaiting channel → In progress) and the publish-start hook's move are conditional on the current status (WHERE status = …), so neither overwrites a move a user made a moment earlier. Trigger debounce uses a time-bucketed job id plus a Redis set of product ids, so no trigger is lost while a job runs (plan §4.4).
  • Events growth is bounded by the retention cron. ITEMS_CHANGED is logged only when the affected count or the sub-type set changes, not on every re-evaluation.
