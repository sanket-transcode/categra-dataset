Action Center V2 — fix state: issues and solutions

Each issue below has the problem, where it lives in the code, a realistic example and the recommended solution. It's based on a static read of api/ and webapp/ as of 2026-11-02. Nothing was run against a database.

How fix state works today

Fix state is computed when it's read, never stored. One SQL CASE in buildItemFixCte (issue-tickets.sql.ts:314) gives each ticket item (a variant or the parent) one of four states. summariseFixStates (issue-ticket-primary-actions.ts:15) then rolls the items up into one state for the ticket.

StateBadgeItem rule (first match wins)
NOT_APPLICABLEno badgeChannel-level types, PRODUCT_TYPE_CHANGED, FBA stock
PUBLISHINGPublishing…sync_in_progress on PCM/VM (Amazon) or PC/PVC (Shopify) in scope
READY_TO_PUBLISHSet · not publishedPrice: price baseline + live price > 0 · Stock: mapped non-FC warehouse has stock (> threshold for LOW) · STOCK_SYNC: always · Main image: media baseline + allowed-extension main image · Listing / Shopify not active: OUT_OF_SYNC or any price/media baseline
NOT_FIXEDNot set in CategraEverything else

Ticket roll-up: no items → not applicable. Only publishing (and not-applicable) items → publishing. Otherwise the lowest rank wins: READY_TO_PUBLISH 0 < NOT_FIXED 1 < PUBLISHING 2 < NOT_APPLICABLE 3. The API also returns fixStateCounts, but the webapp never reads it.

How the solutions decide "ready"

The solutions below all split the question the same way:

  • Is there an unpublished change? The baseline answers this. A baseline row exists only while Categra differs from what was last sent, and it's deleted when the value goes back or the publish succeeds.
  • Is it the change this issue needs? The baseline's content answers this. Every baseline records which value changed and what was last sent:
    • tbl_price_sync_baselines.price_type + previous_price_data;
    • tbl_attribute_sync_baselines.attribute_id / hierarchy_id + previous_sync_value;
    • tbl_variant_attribute_sync_baselines.product_variant_attribute_id;
    • tbl_product_media_sync_baselines.previous_sync_value, a list of {digitalAssetsId, isMainImage, sequence, …};
    • tbl_misc_sync_baselines.baseline_type (category, condition, shipping template, …).
  • Was the fix already sent? Only this question uses time: a successful publish after the item appeared (#8, #10).

Don't compare edit time with the item's created_at to decide "ready", for two reasons. An unpublished edit made before the issue appeared can still be the fix. And the evaluator deletes and re-creates an item whenever its (variant, sub-type) identity changes (issue-ticket-evaluator.service.ts:354-365), which resets created_at.

Ticket-level roll-up

1. Roll-up is too optimistic

HighSmall

Problem

A ready item outranks a not-set item, so one ready variant makes the whole ticket "Set · not published". The primary button then becomes "Review & publish" and opens the publish tab instead of the fix tab. The per-state counts that would show the real split are sent to the webapp but never shown.

Where: issue-ticket-primary-actions.ts:15-20 (rank sort), :58-63 (button) · ISSUE_TICKET_FIX_STATE_RANK in constants.ts:2719 · action-center-v2-ticket-card.tsx:230 · fixStateCounts is unused in the webapp.

Example

MISSING_PRICE on "Linen Shirt" · Amazon DE · 12 variants. The user sets a price for S / White only.

Card: Set · not published + Review & publish. The user publishes, believes the ticket is done, and 11 variants still have no price.

Solution

  1. Make the roll-up pessimistic. If any item is NOT_FIXED, the ticket is NOT_FIXED. Ready only when no item is not set. Swap the first two ranks: NOT_FIXED 0, READY_TO_PUBLISH 1, PUBLISHING 2, NOT_APPLICABLE 3. Keep the existing "only publishing → publishing" short-circuit.
  2. Show the split on mixed tickets. The webapp already gets fixStateCounts. When the ticket has more than one actionable item and the states are mixed, render 1 / 12 set instead of the plain label. Use the same text in the dialog header and the context-bar hint.
  3. The button follows the new roll-up. Mixed → type's fix action ("Open Price") to the fix tab. "Review & publish" only when nothing is left not set.
  4. Dialog: sort items not set → ready → publishing so the outstanding ones are on top.

No schema change. The CSV stays per item.

2. Publish hook moves the whole ticket to Awaiting channel

HighSmall

Problem

When a publish starts, the hook moves a To-do / In-progress ticket to AWAITING_CHANNEL if any of its items is ready or publishing. The items that are still not set go with it. The evaluator moves the ticket back to In progress only once the fixing publish is evaluated. If that result never reports, it waits for the nightly sweep. Until then the unfixed variants are out of the work lanes.

Where: issue-ticket-publish-hook.service.ts:59-94 (the fixable set → ticketIds) · release in issue-ticket-evaluator.service.ts:390-414.

Example

LOW_STOCK on "Trail Runner" · Shopify · 8 variants. The user maps a warehouse for 2 sizes and the stock publish starts.

The ticket jumps to Awaiting channel. The other 6 variants are still low on stock, but nobody sees them in To-do. If the stock result doesn't come back, the ticket sits there until the nightly sweep, then reappears in In progress rather than To-do.

Solution

  1. In the hook, move a ticket only when none of its actionable items are NOT_FIXED after the publish starts. That means every item is ready, publishing or not applicable. Resolve fix states for all items of the candidate tickets, not just those in the publish scope.
  2. When only some items are covered, keep the status. Write an activity event (e.g. PUBLISH_STARTED with "2 of 8") so the timeline still shows that something was sent.
  3. This matches the pessimistic roll-up from #1. A ticket is "awaiting the channel" only when the user has nothing left to do on it.

3. An in-flight publish is hidden when other items are not set

LowSmall

Problem

With some items publishing and others not set, the roll-up shows the not-set state. The card gives no hint that a publish is already running for part of the ticket.

Where: summariseFixStates · card badge in action-center-v2-ticket-card.tsx:230-237.

Example

MAIN_IMAGE on "Ceramic Mug" · 5 colour variants. 3 are being published, 2 still have no image. The card shows only Not set in Categra. A teammate opens it, re-uploads the 3 images that are already on their way, and publishes again.

Solution

Render a second, quiet chip from fixStateCounts.PUBLISHING when it's above 0 and the ticket isn't fully publishing: 2 / 5 set 3 publishing. Webapp only. Show the same per-item badges in the dialog, as today.

Rules

4. Product-level flags apply to variants (only one edge to check)

LowCheck only

Problem

This turned out to be mostly not an issue. Forward sync flags only one level, and the fix-state SQL derives the state one way, parent → variant, which matches it:

  • Parent publish: only the PCM row gets sync_in_progress = true. The variant (VM) rows aren't touched, because publishing the product sends every variant.
  • Variant-only publish (marketplaceIsVariantSync): only the selected variants' VM rows get the flag. The PCM row doesn't.
  • Variant item: publishing if the parent PCM or its own VM is in progress.
  • Parent item: PCM only; the VM branch requires a variant_id. A few variants in flight don't make the parent publishing.

The same parent → variant rule applies to OUT_OF_SYNC. After the #5 rework that's only the fallback for listing issues that name no attribute.

The remaining edge. In an incremental publish where the parent publishes, marketplaceIsVariantSync = !parentPublishes is false. So only the PCM row is flagged, and only the parent scope goes into tbl_publish_inflight_scopes. If that publish can send the parent plus only some variants, every variant item shows "Publishing…", including the ones not sent.

Where: amazon-product-fs.service.ts:1925-1945 (parent flag, marketplaceIsVariantSync), :2090-2115 (variant flag), :2175 · scopeFlagSql in issue-tickets.sql.ts:185-218.

Example

Only if the edge exists: MISSING_PRICE on "Linen Shirt" · Amazon DE · 12 variant items. An incremental publish sends the parent's title change plus the prices of 2 variants. Only the PCM row is flagged, so all 12 items show Publishing…, and the 10 variants still without a price disappear from "not set".

Solution

  1. No change to the flag toggling or to scopeFlagSql. The one-way parent → variant derivation is correct.
  2. Check: does the variant loop in the parent-publishes incremental branch send every variant, or only the selected ones? If every variant, close this item.
  3. Only if it sends a subset: in that branch also set sync_in_progress on the VM rows of the variants actually sent, and register their variant scopes. Variant items then read their own flag, and the parent flag no longer stands in for "all variants". The SQL stays as it is.

5. Listing types turn amber after unrelated edits

MediumMedium

Problem

For AMAZON_LISTING_BLOCKER / WARNING / NOT_SEARCHABLE and SHOPIFY_NOT_ACTIVE, "ready" means "anything in scope differs from the channel". That's OUT_OF_SYNC, or any price baseline, or any media baseline. The rule doesn't check whether the changed value is the one the issue is about.

Where: issue-tickets.sql.ts:333-334.

Example

A blocker on "Desk Lamp" · Amazon UK: "Missing required attribute: voltage". A pricing manager drops the price by £2. A price baseline is created.

The blocker ticket shows Set · not published + Review & publish. Voltage is still empty, and the publish is rejected again.

Solution

  1. Match the baseline to the issue's attribute. When the item's error rows (tbl_channel_product_errors) carry an amazon_attribute_hierarchy_id, the item is ready only if an attribute baseline exists for the same scope and the same attribute:
    • parent: tbl_attribute_sync_baselines.hierarchy_id on (product, channel, marketplace);
    • variant: the matching tbl_variant_attribute_sync_baselines row, resolved through product_variant_attribute_id → attribute.
    In the example, voltage has no baseline, so the item stays not set.
  2. Issues that name a product type or category match a tbl_misc_sync_baselines row of the matching baseline_type (e.g. AMAZON_CATEGORY).
  3. Issues that name no attribute (generic suppression, SHOPIFY_NOT_ACTIVE): ready when the item's own scope has any attribute or misc baseline, or is OUT_OF_SYNC (own row, or the parent row for a variant item; see #4).
  4. Drop the price and media baselines from this rule. Those changes have their own ticket types.
  5. Use a more honest label for the fallback case in rule 3: Edited · not published (see #11). An edit there isn't proof of a fix until Amazon re-validates.

Edit time plays no part: an unpublished voltage change made before the blocker appeared is still the fix.

6. Buy box types treat any price edit as the fix

MediumMedium

Problem

  • All four price types are ready as soon as any price baseline exists and the price is above 0. The baseline's price_type is ignored, so a list price, sale price or business price change counts too.
  • For BUY_BOX_LOST / AT_RISK / INELIGIBLE the rule never compares the new price with the buy box or expected price.
  • Ineligibility is often not about price at all: account metrics, fulfilment, condition.
  • The PRICE publish kind only lists MISSING_PRICE. A price publish therefore never moves a buy box ticket to Awaiting channel, even when the badge said "ready".

Where: PRICE_ISSUE_TYPES branch in issue-tickets.sql.ts:319-320 · ISSUE_TICKET_ISSUE_TYPES_BY_PUBLISH_KIND.PRICE in constants.ts:2698.

Example

BUY_BOX_LOST on "USB-C Hub" · Amazon FR. Buy box at €23.49, our offer at €24.99. The user changes the price to €24.89.

The card turns Set · not published. After the publish the buy box is still lost, and the ticket stays in To-do with no "awaiting" step.

Solution

  1. All price types: count only baselines whose price_type is OFFER_PRICE. A business-price edit on a MISSING_PRICE item no longer marks it ready. SALE_PRICE could count if the sale is live now; leave that out until someone asks for it.
  2. LOST / AT_RISK: ready only when the live price is at or below the target from the buy box data the detector already reads. The target is the buy box landed price for LOST and the expected price for AT_RISK. Otherwise not set, with a hint like "€24.89 is still above the buy box (€23.49)".
  3. INELIGIBLE: treat it as not applicable for fix state, unless the eligibility reason is price. Point the primary action at the reasons ("View eligibility"), not the price tab.
  4. Add LOST / AT_RISK to the PRICE publish kind, so a qualifying price publish moves them to Awaiting channel like MISSING_PRICE.

7. STOCK_SYNC is always "Set · not published"

LowSmall

Problem

STOCK_SYNC is hard-coded to ready unless it's FBA or publishing. The amber badge is always on, so it tells the user nothing. The real problem is a failed or diverged stock sync, which has nothing to "set".

Where: issue-tickets.sql.ts:324.

Example

STOCK_SYNC on "Yoga Mat" · Shopify: the last stock push failed with a 422. The card says Set · not published, and the button says "Review & publish". Nothing was set, and the user doesn't know a retry is the fix.

Solution

Classify STOCK_SYNC as NOT_APPLICABLE for fix state (no badge). Give it a dedicated action, "Retry stock sync", that re-queues the stock push for the ticket's items. Publishing still shows while the retry is in flight.

8. Stock "ready" never checks what was pushed

MediumMedium

Problem

  • OUT_OF_STOCK / LOW_STOCK are ready whenever Categra's mapped non-FC warehouses hold stock (above the threshold for LOW).
  • Nothing compares that with the quantity last pushed to the channel. "Not published" can't be told apart from "published, the channel hasn't caught up".
  • Not set mixes two different causes: no warehouse mapped, and no stock.

Where: issue-tickets.sql.ts:321-330 and the st lateral at :339-360.

Example

OUT_OF_STOCK on "Water Bottle" · Amazon DE (FBM). 40 units arrive and the stock push succeeds. Amazon's listing report still shows 0 for a few hours.

The card stays Set · not published, so the user publishes again. On a second product, 50 units sit in an unmapped warehouse and the card says Not set in Categra. The stock is set; the mapping is what's missing.

Solution

  1. Stock has no baseline table, so compare Categra's quantity with the last successfully pushed quantity for the scope (the stock sync's own record of what it sent):
    • Different and enough stock → ready ("Stock set · not published"). This is the stock equivalent of "a baseline exists"; no time condition.
    • Equal, and that push succeeded after the item appeared → waiting for channel (see #10). Time is used here only to answer "was the fix already sent?". An older push of the same quantity is what the channel already saw when it raised the issue.
  2. Split not set by cause and show it as hint text: "No warehouse mapped to this channel" versus "No stock in mapped warehouses".

Check first: where the stock sync stores the last pushed quantity per channel / marketplace / variant. If it doesn't store it, record it on a successful push before building this.

9. Main image "ready" only checks the file extension

LowSmall–Medium

Problem

Ready means a media baseline exists and a main image (channel or master) has an Amazon-allowed extension. Amazon's actual rejection reasons aren't checked: pixel size, white background, watermark. Any media change also counts, even on a different image.

Where: issue-tickets.sql.ts:244-248, :279-286, :331-332.

Example

MAIN_IMAGE on "Leather Wallet" · Amazon UK, rejected because it's under 1000 px. The user adds a lifestyle shot as a secondary image, which creates a media baseline. The card shows Set · not published, while the main image is still the 800 px file.

Solution

  1. Compare against the baseline's main image. Ready when the media baseline exists and the current main image differs from the main image in the baseline:
    • current: tbl_product_media_linkers.digital_assets_id where is_main_image (channel scope, else master);
    • baseline: the digitalAssetsId of the previous_sync_value element with isMainImage = true.
    A secondary-image change keeps them equal, so the item stays not set. No time condition.
  2. Reuse the pre-send image checks forward sync already runs (extension, plus dimensions where they're stored) instead of a separate extension list.

10. After a successful publish the badge falls back to "Not set in Categra"

HighMedium

Problem

Ready is based on "Categra differs from the channel": a baseline row, or OUT_OF_SYNC. Both are out-of-sync markers, so a successful publish clears them. Between the publish succeeding and the channel clearing the issue, the item matches no ready rule and falls through to Not set in Categra. This is the worst message to show right after the user fixed it. Buy box tickets (#6) aren't moved to Awaiting channel at all, so they show this in a work lane.

Where: the ready rules in issue-tickets.sql.ts:319-334 all depend on baselines / OUT_OF_SYNC · release timing in issue-ticket-evaluator.service.ts:390-414.

Example

MISSING_PRICE on "Garden Hose" · Amazon IT. The user sets €19.90 and publishes. The feed succeeds and the baseline is removed. Amazon's listing still reports no offer for ~20 minutes.

The card (now in Awaiting channel) reads Not set in Categra. The user opens it, sees the price is set, and loses trust in the board.

Solution

  1. Add a fifth state, AWAITING_CHANNEL, with the badge Published · waiting for channel. An item gets it when:
    • it's open;
    • it has no out-of-sync marker;
    • its scope had a successful publish after the issue appeared (see "Which created_at" below).
  2. For the publish time, use the scope row's last-success timestamp, or the publish-start / result events the ticket already records.
  3. Why time is right here: this state is about whether the fix was already sent, not whether the edit is relevant. Relevance was already settled by the baseline rules before the publish cleared them. Without the time bound, any publish from before the issue appeared would count as "fix sent".
  4. Which created_at: because the evaluator re-creates items when their sub-type changes, compare with the ticket's created_at or the item identity's first event, not the item row's created_at.
  5. Rank it with publishing in the roll-up. Not set still wins, per #1.
  6. Cheaper fallback: when the ticket status is Awaiting channel, show the waiting badge instead of the computed fix state.
Labels

11. "Not set in Categra" is the wrong message for most types

MediumSmall

Problem

One label covers every type. It fits MISSING_PRICE and MAIN_IMAGE. It's wrong when a price exists but loses the buy box, when an attribute has a wrong value, or when stock exists but isn't mapped. "Set · not published" has the same problem for listing types, where an edit isn't proof of a fix.

Where: ActionCenterV2_FixState_* and ActionCenterV2_ContextBar_FixHint_* in webapp/src/services/translationServices/*/action-center.ts.

Example

BUY_BOX_LOST on "USB-C Hub". The price is €24.99 and visible on the pricing tab, yet the card says Not set in Categra.

Solution

Use per-type keys with a generic fallback: ActionCenterV2_FixState_<STATE>_<ISSUE_TYPE>, falling back to ActionCenterV2_FixState_<STATE>. Suggested copy:

Issue typesNot fixedReady
MISSING_PRICENo price setPrice set · not published
BUY_BOX_LOST / AT_RISKPrice above buy boxPrice beats buy box · not published
OUT_OF_STOCK / LOW_STOCKNo warehouse mapped / No stockStock set · not published
MAIN_IMAGEMain image needs replacingNew image · not published
Listing / Shopify not activeNeeds a fixEdited · not published
fallbackNeeds a fixSet · not published

Add all five languages in the same change.

12. An item with no computed state shows "Not set"

LowTiny

Problem

If the fix-state query returns no row for an item, the card falls back to NOT_FIXED. That happens when the ticket's channel row is gone, or a chunk query fails silently. A data gap reads as "you haven't done this".

Where: issue-tickets.service.ts:554.

Example

A Shopify channel is deleted while the evaluator hasn't cleared its tickets yet. Its open tickets show Not set in Categra on every card until the sweep runs.

Solution

Fall back to NOT_APPLICABLE (no badge), and log the missing item ids once per read so the gap is visible.

Performance & workflow

13. Fix state is recomputed per item on every read

MediumMedium

Problem

Every board page, dialog, product drawer and CSV export runs buildItemFixCte for every item of every ticket loaded. Each item runs several correlated subqueries:

  • scope flags twice, each with two EXISTS branches;
  • both baselines;
  • the live price, as two ordered subqueries;
  • FBA and warehouse laterals.

Nothing is cached. Cards only need the counts and the roll-up, not every item's state.

Where: issue-ticket-fix-state.service.ts (2000-item chunks) · issue-tickets.service.ts:441.

Example

A board lane with 50 apparel tickets, each with 60–200 variant items, is ~6,000 items. The fix-state SQL runs 3 chunks of ~10 subqueries per item on every lane load and every "load more". A CSV export of 40k items is about 20 chunks.

Solution

  1. Cards: return only fixStateCounts and the roll-up, computed in SQL with a GROUP BY ticket_id over item_fix. Fetch per-item states only for the dialog / drawer of one ticket.
  2. Join once instead of per item: pre-aggregate the scope rows once per (product, channel, marketplace) in a CTE, then join the items to it. That replaces repeating the EXISTS per item.

14. No filter or bulk path for ready tickets

LowMedium

Problem

The board can't filter or sort by fix state. A user can't ask "show me everything that's set but not published" and send it together. They have to open each product and publish one at a time.

Where: buildTicketBase (issue-tickets.sql.ts:66) has no fix-state condition · the webapp filter bar has no fix-state facet.

Example

After a pricing review, 35 MISSING_PRICE tickets across 35 products are ready. The user opens 35 product pages and clicks publish 35 times.

Solution

  1. Filter: add a "Fix state" facet using the ticket roll-up (after #1): Needs a fix / Ready to publish / Publishing / Waiting for channel. Do it as an EXISTS over item_fix in buildTicketBase.
  2. Bulk publish: with the filter on Ready, offer "Publish N ready". It calls the existing price / stock / forward-sync publish flows, grouped by channel and publish kind. The publish-start hook then moves the tickets as it does today.
Suggested order
  1. #1 + #2 + #3: pessimistic roll-up, counts on the card, hook moves only fully covered tickets. Small change, biggest trust gain.
  2. #10 + #11 + #12: the waiting-for-channel state and per-type wording. Stops the board contradicting what the user just did.
  3. #4: check only: confirm whether a parent-publishes incremental publish can send a subset of variants.
  4. #5 – #9: per-type rule fixes (listing, buy box, STOCK_SYNC, stock, main image).
  5. #13 + #14: counts-only card query, then the fix-state filter and bulk publish.
