Action Center V2: three decisions

The recommended answer to each of the three open questions in the V2 brief, with the design behind it: ticket storage, workflow lanes, and how a ticket can show the live channel state without confusing a user who has already fixed the issue in Categra.

Scope api · webapp · db-migrations Baseline action-center-v1-explained.html Taxonomy Command Center attention families Date 2026-10-23
1 · Computed or stored?
Store tickets in a table. Keep detection computed.

A shared evaluator works out the issues from the external state and writes the result to tbl_issue_tickets. Statuses, assignees, snoozes and the audit trail are stored next to the ticket, not projected over it.

Design →
2 · Three lanes?
Yes: To do · In progress · Awaiting channel.

Lanes stop meaning "is it solved" (only the system decides that). They now mean "who is the ticket waiting on": us, a teammate, or Amazon/Shopify.

Design →
3 · External vs local
The channel decides if a ticket exists. Categra adds a fix state.

Each ticket item gets a read-time state: Not fixed → Ready to publish → Publishing. The badge and the primary button follow it, so "I already added the price" is answered on the card.

1Tickets: computed or a managed table

Today a ticket exists only while a SQL pass over the catalog produces it, and three side tables try to remember what the team did with it. V2 needs a ticket to be a real record.

1.1Verdict

Recommendation

Computed detection, stored tickets. One evaluator (a pure function over the external state, built on the Command Center SQL backbone) runs for a scope whenever a system event touches that scope. It diffs its result against the stored tickets of the scope: it creates new ones, updates the ones still present, and deletes the ones that are gone. The user-owned fields (stage, assignee, snoozes) live on the ticket row and its side tables. The evaluator never rewrites them.

  system event (publish result, import, stock/price publish, notification, sweep)
          │  scope = account × channel × marketplace × [products] × [issue types]
          ▼
   IssueTicketEvaluatorService.evaluateScope()  reads external state only (§3.2)
          │  current issue set for the scope
          ▼
   diff vs tbl_issue_tickets (same scope)
     ├─ new key           → INSERT ticket + items   → event CREATED / REAPPEARED
     ├─ key still present → UPDATE items, counts     → event ITEMS_CHANGED (if the count or sub-type set changed)
     └─ key gone          → DELETE ticket (cascade)  → event CLEARED
          │
          ▼
   user acts on stored rows: stage · assignee · snooze   → events STATUS_CHANGED / ASSIGNEE_CHANGED

1.2Why: the management needs decide it

Every requirement in the brief needs one of two things: a stable record to attach state to, or a moment when something changed. Computing tickets on every read gives neither. The v1 code has to work around this on every read: it reconciles overlays against live rows, guesses clearances, writes lifecycle events from a read path, and keeps a 15-second in-process cache so three lane requests don't each rebuild the snapshot.

The table is only as fresh as its triggers. Every pipeline that writes the external state must enqueue an evaluation (§1.7). The nightly sweep catches anything missed. Tickets must never be cleared outside the scope that was evaluated (§1.6 rule 2).

1.3Ticket identity: one universal key

Every ticket uses the same four segments in the same order. A segment that does not apply to the issue type is 0, never left out. The account is not part of the key. Uniqueness is per account.

  • The 0 exists only in the key. The key columns are nullable foreign keys (NULL when a key doesn't apply), and the generated ticket_key writes COALESCE(col, 0). The key is never NULL, so one plain unique index on (account_id, ticket_key) enforces identity.

1.6The evaluator

One service (IssueTicketEvaluatorService) and one BullMQ queue (ISSUE_TICKET_EVALUATION, processed in api-worker, following the READINESS_RECALCULATION pattern).

1.6.1Input: a scope

{
  accountId, channelId,
  amazonMarketplaceId?   // omitted = every active marketplace of the channel
  productIds?            // omitted = every published product in the channel scope
  issueTypes?            // omitted = every family that applies to the channel type
  source                 // trigger name, recorded on events
}

1.6.2Steps

  1. Detect. Run the family detectors for the scope against the external state (§3.2). These are the Command Center attention SQL builders, refactored to return per-unit rows instead of aggregated cards and filtered to productIds. Parents with variants are folded: the ticket is the parent product and its variants become items.
  2. Load current. Select the stored tickets and items of exactly that scope (same channel, marketplaces, products, issue types).
  3. Diff and write in one transaction, under a Postgres advisory lock on (account_id, channel_id):
    • A new key is inserted with status TODO. If the events table has a past CLEARED for that key, the event is REAPPEARED, otherwise CREATED.
    • A key that still exists has its items replaced, and affected_variant_count and last_evaluated_at updated. ITEMS_CHANGED is logged only when the count or the set of sub types changed. The detector keeps one item per (variant, sub type), collapsing repeats such as one METRIC_BAD per bad metric.
    • A key that is gone is deleted (items and snoozes cascade) and CLEARED is logged.
  4. System stage moves (§2.3) are applied in the same transaction.
  5. Publish a lightweight "tickets changed" signal for the account. The page can pick it up later; it is not needed for correctness.

1.6.3Rules

  1. The evaluator writes system columns only. It never touches status (except the moves in §2.3), the assignee or snoozes.
  2. It never clears outside its scope. A product trigger for products [12, 15] in DE cannot delete product 20's tickets, or tickets of a family it did not evaluate.
  3. Jobs are deduplicated and debounced without losing ids. The job id is account:channel:marketplace:issueTypes:bucket with a short delay (a constant, e.g. 10 s) and bucket = floor(now / delay), as the readiness trigger does, so a trigger arriving while a job runs lands in the next job instead of being dropped as a duplicate id. Product ids collect in a Redis set per job id (SADD) that the job reads and deletes atomically when it starts. A 5 000-product import produces a handful of evaluations, not 5 000.
  4. The channel must be connected. While a CONNECTION ticket exists for a channel, product-level evaluation of that channel is skipped (§4), because the external state cannot be trusted.

2Are three lanes needed?

"Mark resolved" is gone and only the system clears tickets. The question is whether the lanes still mean anything.

2.1Verdict

Recommendation

Keep three lanes, with new meanings: To do · In progress · Awaiting channel (renamed from "Pending verification"). A lane says who the ticket is waiting on: nobody has picked it up, a teammate is working on it, or the fix is out and Amazon/Shopify still has to confirm it. None of them means "solved", because a solved ticket disappears.

2.2The three lanes

To do TODO
Detected, nobody has started.
Entered: new or re-appeared ticket · user move
In progress IN_PROGRESS
Someone is fixing it in Categra.
Entered: user move · primary action click · channel still reports the issue after a publish
Awaiting channel AWAITING_CHANNEL
Fix published, or a case raised with the channel. Waiting on them.
Entered: user move · a publish starts on the product page

Every lane is left the same way: the evaluator clears the ticket, or the user moves it. A ticket that is snoozed for the current user is hidden from all three lanes for that user only.

2.4Alternatives rejected

OptionWhy not
No lanes: one sorted listLoses "what is mine to do now" vs "what is out of our hands". A team would re-open tickets that are only waiting for an Amazon feed.
Two lanes (To do / In progress)A published fix that Amazon has not confirmed yet (feed processing, issue refresh, up to hours) sits in In progress next to real work. "Awaiting channel" is the stage this redesign makes visible.
Third lane fully system-owned (derived from "publishing")A seller also waits on the channel when no publish is involved (a support case, a compliance appeal), so the user must be able to move a ticket there too. The publishing signal shows as a badge (§3) instead.

2.5Lane behaviour in the UI

  • Each lane loads its own page from POST issue-tickets/tickets, with infinite scroll and server-side order. Lane counts come from /counts.
  • A move, assign or snooze updates the card in place from the mutation response and adjusts the two lane counts locally. There is no full reload and no periodic refresh.
  • Cards have a fixed size (image box capped, e.g. 44 × 44, name clamped to two lines), so lanes stay aligned and virtualise cleanly.
  • Clicking a card opens the ticket dialog (items, evidence, history). The separate issue page is removed.

3External state vs what is in Categra

The channel decides whether a ticket exists. The confusing case is a user who has already added the price or image in Categra and still sees the ticket, because the change has not reached Amazon or Shopify yet.

3.1Verdict

Recommendation

Same ticket, plus a system-derived fix state. Whether a ticket exists depends only on the published / live state. Each item also carries a fix state that compares Categra to what is live: NOT_FIXED (it is missing in Categra too), READY_TO_PUBLISH (Categra has it, the channel doesn't), or PUBLISHING (a publish of that scope is in flight). The fix state drives the card badge, the context bar and the primary button. It never creates or clears a ticket.

One divergence to settle

For listings with mapped non-FBA warehouses, the Command Center today judges stock on the warehouse quantity (local) and calls a remote mismatch STOCK_SYNC. Under "purely external", a listing with 5 in the warehouse and 0 on Amazon is OUT_OF_STOCK with fix state READY_TO_PUBLISH. The CC stock classifier would have to move to the remote quantity too, or the two pages will disagree. See §5 #2.

3.6Why the fix state is read-time, not stored

Read-time (recommended)
  • Local edits need no trigger: the ticket table changes only on external events, as the brief requires.
  • Always exact: it is a join of the visible page's items to the baselines and the in-flight flags (≤ one page of rows).
  • Filterable ("Ready to publish" in the filter dialog) through the same join.
Stored (rejected)
  • Every price / media / attribute save, revert and publish start would have to update ticket items. That is the trigger surface of the whole product editor.
  • Any missed write leaves a wrong badge, which is the confusion this is supposed to remove.

4Edge cases

CaseBehaviour
Channel connection lostA CONNECTION ticket opens. The channel's product tickets are frozen (not re-evaluated) until reconnect. The reconnect trigger then evaluates the whole channel.
Product deleted / unlisted from a channelDelete: clearScope runs synchronously in the delete transaction, before the delete, and clears its tickets (variant delete: removes its items and recounts) with source SCOPE_REMOVED, so CLEARED is audited. A queued evaluation would run after the cascade had already removed the rows. Unlist: no row is deleted, so the normal queued evaluation clears it. The product_id / variant_id FK cascades only catch missed paths (silently, without an event); the nightly sweep fixes counts they leave stale.
Channel deletedFK cascade on channel_id. Audit rows stay (keyed by ticket_key).

A new variant gets the same issueAn item is added to the existing ticket. There is no new ticket and the stage is unchanged.
Issue flaps (clears, then re-appears within minutes)New row, REAPPEARED, starts in To do. The debounce in §1.6.3 absorbs most flaps within one burst of events.
Snoozed ticket is clearedThe snooze is cascade-deleted. If the issue re-appears it is not snoozed.
Assignee loses channel access or leavesThe ticket shows as unassigned (the assignee is filtered at read time). The next assignment overwrites it.
User acts on a ticket cleared meanwhile404 TICKET_CLEARED. The card is removed quietly.

Same seller in several Categra accountsTickets are per account. Fan-out channel-health triggers enqueue one evaluation per affected account.
