Ticket schema & publish flow: open questions

Answers to seven questions about the ticket tables and the publish button, checked against the Command Center constants, the channel-health rules and the product page code. All answers were accepted; §8 lists the changes now applied to the schema, plan and solutions docs.

1issue_type_rank & priority

Both columns are a fixed function of issue_type. A stored copy only helps if the value can differ between two tickets of the same issue type, and today it can't.

1.1What they hold

ColumnValueSource today
issue_type_rankPosition of the issue type in the board order: CONNECTION = 1, ACCOUNT_HEALTH = 2, … MISSING_PRICE = 6 … BUY_BOX_AT_RISK = 18.COMMAND_CENTER_ATTENTION_FAMILY_ORDER (api/…/core/constants/constants.ts:2489)
priorityRed / Yellow / Blue.COMMAND_CENTER_ATTENTION_SEVERITY (constants.ts:2468): critical → Red, warning → Yellow, info → Blue.

Both maps are keyed by issue type alone. Every MISSING_PRICE ticket gets rank 6 and Red, and every LOW_STOCK ticket gets rank 8 and Yellow. The evaluator writes them, but it adds nothing: it copies the constant into the row.

1.2Where they are used

1.3Dynamic issue-type order

Suppose the order later becomes a per-account setting. For example, account A wants BUY_BOX_LOST above LOW_STOCK.

Stored rank
  • Saving the setting must run UPDATE tbl_issue_tickets SET issue_type_rank = CASE issue_type … END WHERE account_id = A, which can touch about 50 k rows on a large account.
  • The evaluator must read the account's order on every write, or new tickets get the old rank.
  • If any write path forgets, the board sorts wrong with no error. A global order change needs a backfill at deploy.
Computed rank
  • The API passes the order array it already holds (the constant today, the account setting later) into the query.
  • Changing the order is one setting write. No ticket row changes.
  • The same resolver feeds the CSV, the drawer and the board, so they can't disagree.
-- lane page with a computed issue-type order
SELECT t.* FROM tbl_issue_tickets t
WHERE t.account_id = :accountId AND t.status = :status /* + filters, snooze rule */
ORDER BY array_position(:issueTypeOrder, t.issue_type),      -- '{CONNECTION,ACCOUNT_HEALTH,…}'
         t.affected_variant_count DESC, t.product_id NULLS FIRST, t.channel_id, t.amazon_marketplace_id NULLS FIRST
LIMIT 30 OFFSET :offset

1.4Cost of computing them

  • What we lose: the lane index can no longer return rows already in order. Postgres reads the lane's matching rows (served by (account_id, status)) and keeps the top offset + 30 in a top-N heap sort.
  • How big that is: schema §9 sizes a large account at about 50 k open tickets. A To do lane of 40 k narrow rows sorts in tens of milliseconds, and channel, market and issue-type filters usually cut it far below that.
  • Why that's acceptable: the counts query (schema §6.2) already reads every row of every lane on each board load. The lane page now does work of the same size, not a larger kind.
  • Priority filter: issue_type = ANY(…) is a plain column filter, so it stays indexable.
Effect on affected_variant_count

Once the first sort key is computed, the stored affected_variant_count no longer gives an index-ordered scan either. It's still worth storing: computing it means joining and aggregating the items (a few hundred thousand rows on a large account) for the whole lane on every page. Rank and priority are a per-row lookup with no join, so they cost nothing to compute.

1.5When storing would be right

Priority would have to be stored if it varied within one issue type. The channel-health rules already have that detail: channel-health.derivation.ts gives ACCOUNT_DEACTIVATED the severity critical and ACCOUNT_AT_RISK the severity at_risk. The Command Center then flattens both to the ACCOUNT_HEALTH family's single severity, so V2 copies that and both are Red. If we ever wanted C1 (at risk) Yellow and C2 (deactivated) Red, the evaluator would compute priority from the ticket's items, and it would become stored data. Until then, derive it.

Recommendation

Drop issue_type_rank and priority. Add one API resolver (resolveIssueTypeOrder(accountId), resolveIssuePriority(issueType)) that reads the constants today. Replace idx_issue_tickets_lane_order with (account_id, status).

2Sub issue types

The ticket is the unit people work on (product × channel × marketplace × issue type). The sub type describes one problem inside it, so it belongs on the item rows.

2.1Where the sub type lives

  • tbl_issue_ticket_items.sub_issue_type, one row per (variant, sub type). Channel-level and standalone-product items have variant_id NULL.
  • The ticket key has no sub type, so a sub-type change keeps the same ticket. Its stage, assignee and snoozes stay; only the items change.
  • A single sub-type column on the ticket couldn't hold the cases in §2.3 and §2.4, where one ticket has several sub types at once.

2.2Example: C1 at risk, C2 deactivated

Both are Amazon channels. The Command Center shows one Account health card for both, with per-channel chips "At risk" and "Deactivated". V2 stores two tickets because the key contains the channel:

Ticket keyissue_typeItems (variant · sub type)Card shows
productId:0||channelId:1||amazonMarketplaceId:0||issueType:ACCOUNT_HEALTHACCOUNT_HEALTHNULL · ACCOUNT_AT_RISKC1 · "Account at risk"
productId:0||channelId:2||amazonMarketplaceId:0||issueType:ACCOUNT_HEALTHACCOUNT_HEALTHNULL · ACCOUNT_DEACTIVATEDC2 · "Account deactivated"

If C1 later goes from at risk to deactivated, the evaluator keeps the C1 ticket, deletes the ACCOUNT_AT_RISK item and inserts ACCOUNT_DEACTIVATED. The card's reason text changes and the stage and assignee stay.

Small gap found

The schema logs ITEMS_CHANGED only when the affected count changes. For C1 the count stays 0, so the at-risk → deactivated change would leave nothing in the history. Suggested fix: also log ITEMS_CHANGED when the set of sub types changes, with from_value / to_value holding the sub types.

2.4Can a ticket with no variants have several sub types?

Yes. The channel-health rules (api/…/catalog/channel/health/channel-health.derivation.ts) emit some reasons independently of each other:

Issue typeSub types that can coexistExample ticket (variant NULL on every item)
MARKETPLACE_HEALTHAHR_NOT_HEALTHY, METRIC_BAD, POLICY_BAD are separate ifs. Only MARKETPLACE_DEACTIVATED / _AT_RISK exclude each other (one account status).FR: MARKETPLACE_AT_RISK + AHR_NOT_HEALTHY + METRIC_BAD → 3 items
DATA_TRUSTINVENTORY_SYNC_STALE, ORDER_SYNC_STALEShopify store where both syncs are failing → 2 items
AMAZON_LISTING_BLOCKER (standalone product)Any listing bucketsProduct 40, no variants: SUPPRESSION_VISIBILITY + COMPLIANCE → 2 items
CONNECTION, ACCOUNT_HEALTHNone. There is one connection status, and account status is an if / else if.Always 1 item
Catch: the same sub type twice

METRIC_BAD is emitted once per bad metric and POLICY_BAD once per policy (a loop over badMetrics / badPolicies). Two bad metrics on FR would produce two (NULL, METRIC_BAD) items, which the unique constraint (ticket_id, variant_id, sub_issue_type) NULLS NOT DISTINCT rejects. The detector should keep one item per sub type. Which metrics are bad is evidence, and the dialog reads it live like all other evidence (schema §3.2: items copy no evidence).

2.5Command Center hand-off for channel health

  • A Command Center attention card is one family, and its chips can show different reasons per channel. V2's redirect carries { issueTypes: ['ACCOUNT_HEALTH'], channelId: null }, and the board filters issue_type = ANY(…). Both C1 and C2 show, whatever their sub type. Sub type is never a board filter.
  • Gap in the next-action steps: a step such as "Restore access" covers several families (action.families). Today the webapp takes only the lead item's redirect (command-center/_lib/attention-view.ts:419 and :438), which has one family. For V2 the step's redirect must send all of action.families, and send a channelId only when every chip is on the same channel. Otherwise a click on "Restore access" would show the connection tickets and hide the account-health and marketplace-health ones.

3status_changed_at & assigned_at

Keep status_changed_at
  • Every card shows the time in stage ("In progress · 3 d", plan §3.4), so it's read for every card on every page.
  • Taking it from events means finding the latest STATUS_CHANGED / CREATED / REAPPEARED event for each card. That's feasible for 30 cards, but it breaks for any ticket older than the 180-day event retention (see the example below).
  • A future "stuck in stage > 7 days" sort or filter needs it as a column on the ticket. It can't be done by scanning events.
Drop assigned_at
  • No screen shows it. The card and dialog show who is assigned, not since when.
  • The dialog history already shows "Priya assigned to Tom · 2 d ago" from the ASSIGNEE_CHANGED event's occurred_at.
Example: why events alone are not enough

Ticket created on 1 Jan. Moved to In progress on 1 Feb. Nobody touches it after that. On 15 Sep the cleanup cron has deleted both events (older than 180 days). With events only, the card has no stage time left. Falling back to created_at would show "In progress · 257 d", which is wrong, because it has been in progress since 1 Feb (226 d). status_changed_at = 1 Feb gives the right answer at no extra cost.

4assigned_by_user_id

Agreed, drop it. The UI never shows who assigned a ticket, and the audit trail already records it: an ASSIGNEE_CHANGED event stores actor_user_id (who), from_value / to_value (old and new assignee) and occurred_at. If the history ever needs "assigned by", it's already there. Dropping it also removes one FK to tbl_users and one entity association.

5detected_at

Drop tickets.detected_at

The evaluator inserts the row the moment it first sees the issue, and a re-appearance after a clear is a new row. So detected_at always equals created_at. The CSV "detected at" column reads created_at.

Keep items.detected_at, renamed created_at

Items have no other timestamp. An item survives re-evaluations (set diff), and a variant can join an existing ticket later, so its time differs from the ticket's. The dialog shows "since" per variant (plan §3.6).

Example

On Monday, Amazon reports no price for variants 51 and 52 of product 12 in DE. The ticket is created and items 51 and 52 get created_at = Monday. On Thursday variant 53 loses its price too: the same ticket gets item 53 with created_at = Thursday. On Friday the dialog reads "51 · since 4 d", "52 · since 4 d", "53 · since 1 d". The ticket's created_at stays Monday.

Renamed to created_at (2026-10-26): the value is set on insert and never updated, so it behaves exactly like created_at, and the ticket already uses created_at for "first seen". The entity uses timestamps: true, createdAt: 'created_at', updatedAt: false. UI and CSV labels ("since", "detected at") are unchanged.

6issue_type in events

Keep it. The ticket row isn't a reliable place to look it up, because there is no "cleared" status: a cleared ticket is deleted (schema §1.1). The events that matter most refer to tickets that no longer exist:

  • The recent-activity drawer shows "System cleared Desk Lamp · Main image", and the board's issue-type filter (MAIN_IMAGE) must still match that event after the ticket row is gone.
  • REAPPEARED joins occurrences across time. The earlier occurrence's row is long deleted.

The issue type is also inside ticket_key (…||issueType:MAIN_IMAGE), as are the product, channel and marketplace. Filtering with ticket_key LIKE '%issueType:MAIN_IMAGE' can't use an index and relies on string parsing. The copied issue_type is a 64-byte column, and it buys an indexable, typed filter. The same reasoning applies to the copied product_id, channel_id and amazon_marketplace_id.

7Publish from the ticket?

Agreed: no direct publish from the board. The button takes the user to the page that already publishes safely. One refinement: that page isn't always the Channels tab.

7.1Why redirect is better

  • The product page already gates publishing: syncInProgress at channel, marketplace and variant-marketplace level (products/_components/list/List.tsx), unsaved changes (Save_Changes_Before_Publishing_Message), the trial sync limit (Trial_Sync_Actions_Exhausted_Message), and socket listeners that refresh progress (PRODUCT_FORWARD_SYNC_SUCCESS, PRODUCT_ERROR, ATTRIBUTE_SYNC_BASELINES_UPDATED, MISC_SYNC_BASELINES_UPDATED).
  • A publish button on the board, the card and the context bar would need a second copy of all of that, plus sockets on a page the plan deliberately keeps free of live refresh. The two copies would drift.
  • On the product page the user sees what will be published (all pending changes for that channel, not only the ticket's), which a one-click board publish would hide.

7.2Which tab owns the publish

The product page has three separate publish actions, and each issue type is fixed by one of them:

Issue typesDestinationPublish control there
MISSING_PRICE, BUY_BOX_*/products/{id}?q=pricingPrice publish (and auto publish)
OUT_OF_STOCK, LOW_STOCK, STOCK_SYNC?q=stockSave & Publish
Listing blocker / warning, not searchable, Shopify not active, main image, product type changed?q=channelsPublish (forward sync)
Channel-level (connection, health, permission, data trust)Channel managementNone. These are fixed outside Categra or by reconnecting.

So "redirect to q=channels" is right for listing and media issues. Price and stock tickets go to their own tab, because publishing from Channels wouldn't push the price or the stock.

7.4Moving to Awaiting channel

The ticket publish endpoint used to move the ticket to Awaiting channel. Without it, the move is done by the system when a publish starts for the ticket's scope:

  • Hook points: forward sync task created, price publish started, stock publish started (the same pipelines that already enqueue FS_RESULT / PRICE_PUBLISH / STOCK_PUBLISH evaluations when they finish).
  • Which tickets move: To do / In progress tickets in that product × channel × markets scope whose items are "Set in Categra · not published" at that moment. They get a STATUS_CHANGED event with a new source PUBLISH_STARTED.
  • Which don't: a BUY_BOX_LOST ticket on the same product isn't fixed by a price push, so it stays where it is.
Example

Priya opens the Missing price ticket for product 12 · DE, sets €19.99 on variants 51–53 and clicks Publish on the Pricing tab. The price publish starts, and the hook moves the ticket In progress → Awaiting channel (source PUBLISH_STARTED). When the result arrives, the PRICE_PUBLISH evaluation clears the ticket, or moves it back to In progress for the variants Amazon rejected.

The alternative is no automatic move, so users drag cards to Awaiting channel themselves. That's simpler, but the lane stops meaning "waiting on Amazon/Shopify" as soon as someone forgets.

Recommendation

Remove POST tickets/:ticketKey/publish, the TICKET_PUBLISH source and the context-bar Publish button. Route "Review & publish" to the tab that owns the publish (§7.2). Add the PUBLISH_STARTED system move.
