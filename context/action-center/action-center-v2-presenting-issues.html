1 · Core objective

Every ticket should answer two questions at a glance:

  1. Presenting issue: what exactly is wrong, in the channel's own terms. For example "AHR 180", "3 metrics failing", "Compliance · 3 errors", "WEBP not supported".
  2. Life cycle: where the fix stands. Inside Categra that's not set → set, not published → publishing → cleared. For issues only the seller can fix outside Categra it's fix on Amazon → waiting for Amazon's re-check → cleared.

Hard constraint: the board card keeps its exact size and slots. It stays h-38 (152 px) with single-line chip rows. A short presenting text goes into the existing issue-type chip. Everything else goes into one structured tooltip: what the channel reports, recommended steps (in Categra and on the external platform), what clears it, and last checked.

Price and stock tickets already do both. Channel-level tickets (account health, marketplace health, connection, permission, untrusted data) do neither. Several product-level types do only one. This doc goes through all 18 types and proposes one shared model for the board card, sub items, ticket dialog, product issues drawer and context bar.

Static read of api/ and webapp/ as of 2026-11-02; nothing was run against a database. Mocks are drawn at the real card size; Amazon / Shopify menu paths in the steps are approximate.

4 · Root causes

4.1 Evidence returns nothing for channel tickets

IssueTicketEvidenceService.loadEvidence starts with if (ticket.productId === null) return result;. All five channel-level types hit it. The data already exists:

  • tbl_amazon_channel_marketplaces: ahr_status, ahr_score, account_status.
  • tbl_amazon_seller_performance.metrics: every metric's rate / target / cond / from / to, every policy's defects / status, the warnings count, checked_at. AmazonAccountHealthService.getDetail already reads it, but no webapp screen calls it.
  • tbl_channel_sync_failures and DataTrustIssue: cause, since, failure count, siblings.
  • tbl_channel_status_events: every AHR / metric / policy / account-status change with previous and current value.

4.2 Item identity drops the detail

buildIssueTicketDrafts keys items by (variantId, subIssueType), so every METRIC_BAD / POLICY_BAD reason collapses into one item. DetectedIssueUnit only carries sub-type strings, so AHR score, connection reason and data-trust cause never reach the ticket.

4.3 NOT_APPLICABLE hides the badge on every surface

ISSUE_TICKET_NOT_APPLICABLE_TYPES = the five channel-level types + PRODUCT_TYPE_CHANGED, plus buy-box items with non-price reasons (applyBuyBoxTargets). IssueTicketFixBadges returns null and the context bar hides its hint, so "fixed outside Categra" is rendered as "nothing to say".

4.4 The card never shows the sub type

Row 3 is issue-type chip + fix label. When the fix label is generic ("Needs a fix") or missing, the presenting issue only appears in the dialog.

5 · Shared solution model

5.1 Fixed card layout: no new rows, no new chips

Card slots stay exactly as today (h-38, justify-between, single-line rows with overflow-hidden):

  1. Title, 2-line clamp (unchanged)
  2. Scope chips: channel · marketplace · variants (unchanged)
  3. Issue chip + one life-cycle chip, still exactly two chips. The issue chip becomes "Issue type · presenting" with an ⓘ pinned at its end. It's the only thing that shrinks: min-w-0, ellipsis. The life-cycle chip is shrink-0.
  4. Footer: assignee · time in stage | i (SKU / ASIN, product tickets only) · primary button (unchanged). No secondary button and no "checked" text here.

Everything else goes into the ⓘ tooltip: full presenting text, facts table, recommended steps, external link, what clears it, last checked.

Width budget: the lane is min-w-76 (304 px) and grows with flex-1. The text column is roughly the card width minus 64 px thumb, padding and ⋯, so about 190–290 px for row 3. The life-cycle chip takes about 80–110 px, leaving the issue chip about 100–180 px. So:

  • The presenting suffix is kept to ≤ 16 characters ("AHR 180", "3 metrics", "Compliance · 3", "WEBP", "€24.90 › €22.50").
  • If it still doesn't fit, the issue-type part truncates first. The tooltip header always repeats both in full, and the severity stripe and colour still show the category.
  • No presenting (price, OOS, low stock): the chip is exactly today's.

5.2 Presenting issue = presenting on the card

presenting: {
	code: string;                                // 'AHR', 'METRICS_FAILING', 'LISTING_ERRORS', …
	params: Record<string, string | number>;   // { score: 180 }, { count: 3 }, { bucket: 'COMPLIANCE', count: 3 }
	tone: 'red' | 'amber' | 'blue' | 'gray';
} | null

Two translations per code: ActionCenterV2_Presenting_<code>_Short (the ≤ 16-char chip suffix) and ActionCenterV2_Presenting_<code> (the full sentence for the tooltip header, dialog headline and context bar). Both go through getPresentingLabel(ticket, 'short' | 'full') in @/lib/issues, with a humanised fallback.

Computed at read time, not stored (decision D1). Every value already sits in a source table, and most joins already run on each board read inside the fix-state SQL. When the channel has recovered but the ticket hasn't cleared yet, the card can say "Recovered · clears on next check" instead of showing a stale number.

5.3 Facts + recommended steps = the tooltip content

Implemented (rev 2): nothing is fetched when the tooltip opens. Channel tickets carry details (facts, checkedAt, since) on the list card. Product tickets carry cheap per-item extras (price vs target, error count, image format, stock). Steps and "clears when" are built in the webapp from the issue type, sub types, metric keys and those extras. Heavy, low-value data (listing error texts, the data-trust affected count) is left out. The explain shape below is kept for reference only:

explain: {
	headline: Presenting;                    // full sentence
	facts: Array<{
		group: 'AHR' | 'METRIC' | 'POLICY' | 'ACCOUNT' | 'CONNECTION' | 'SYNC' | 'PRICE' | 'LISTING' | 'MEDIA' | 'PRODUCT_TYPE';
		key: string;                         // metric / policy / attribute key → translated, humanised fallback
		value: string | number | null;
		target?: string | null;              // "< 1%"
		status?: 'bad' | 'warn' | 'ok';
		window?: { from: string | null; to: string | null };
	}>;
	steps: Array<{
		where: 'CATEGRA' | 'AMAZON' | 'SHOPIFY';
		key: string;                         // ActionCenterV2_Step_<key>, ≤ ~12 words each
		params?: Record<string, string | number>;
		link?: { kind: 'CATEGRA' | 'EXTERNAL'; url: string; labelKey: string };
	}>;                                       // 2–4 steps; fact-specific steps first (e.g. per failing metric)
	clearsWhenKey: string;                   // ActionCenterV2_ClearsWhen_<issueType>
	since: string | null;
	checkedAt: string | null;
}

Steps are static per issue type / sub type / metric key (a constant map in the API), filled with params from facts. Each step is a few words. External steps name the approximate menu path ("Seller Central › Performance › Account Health"), and only one external link per tooltip is shown as a link. The same explain payload also feeds the dialog (inline, §7) and the context bar tooltip.

Tooltip layout (same on every surface)

  1. Header: full "Issue type · presenting" sentence
  2. What the channel reports: facts table, bad values in red, max ~6 rows then "+n more · open ticket"
  3. Recommended steps: numbered, a platform tag per step, one link
  4. Footer: "Clears when …" · "Checked 3h ago"

Reuse CommandCenterInfoTooltip (portaled, max-h-72-style cap, scrolls) so it matches the identifiers tooltip. It doesn't affect card height because it's portaled.

5.4 External life cycle = new fix state EXTERNAL

A fix state for "only the seller can fix this outside Categra". Every surface already renders fix states through IssueTicketFixBadges, IssueTicketItemFixBadge and getTicketFixHint. On the card it uses the same single life-cycle chip slot, so no extra width.

External link: "Open in Seller Central" / "Open Shopify admin" sits in the tooltip steps and the ⋯ menu, and as a button only in the dialog and context bar. Those already have button rows, so their height doesn't change. The card's primary button stays as it is.

6.3 Connection Both missing

  • Chip suffix: "Not connected" · "Token revoked" (humanised connection reason).
  • Facts: status, reason, last successful check.
  • Steps: Categra: Channel settings › Reconnect → Amazon / Shopify: approve access with the account owner's login → Categra: wait for "Verifying" to clear.
  • Life cycle: NOT_FIXED / RECONNECT → VERIFYING after the OAuth callback → cleared when the probe passes. The reconnect path must fire an issue-ticket trigger (source CHANNEL_HEALTH).

6.4 Permission required Both missing

  • Chip suffix: "Insights role".
  • Facts: missing role (Selling Partner Insights), blocked feature (account health report), since, failure count.
  • Steps: Amazon: Seller Central › Settings › User Permissions, grant the role to the app user → Categra: Channel settings › Reconnect to re-authorise → wait for the next health report.
  • Life cycle: NOT_FIXED / GRANT_PERMISSION → VERIFYING until the next performance report succeeds → cleared.

6.5 Untrusted data Both missing

  • Chip suffix: "Inventory · 6h" · "Orders · 2h".
  • Facts: domain, cause (humanised error code), since / duration, sibling marketplaces healthy/stale (affected count in the dialog only).
  • Steps: Categra: retrying automatically, no action needed yet → if over a few hours, check the channel connection → contact support with the shown cause.
  • Life cycle: EXTERNAL / AWAITING_RECHECK, hint "Retrying automatically · last attempt 10m ago". If a manual retry exists, it's a step link, and VERIFYING shows while it runs.

6.6 Product type changed Both missing

  • Chip suffix: "→ T_SHIRT" (the suggested type; current → suggested in the tooltip).
  • Facts: current type (amazon_product_type_id), suggested type (suggested_product_attribute_group_id), attributes that would need remapping (count).
  • Steps: Categra: open the product's channel tab → review the suggested type → accept and remap attributes, or dismiss → publish.
  • Life cycle (implemented): NOT_FIXED / REVIEW_PRODUCT_TYPE "Review product type". Accepting or dismissing clears the suggestion and the ticket immediately.

6.7 Buy Box ineligible Partial

  • Chip suffix (from the sub type): "Offer" · "ASIN" · "Not featured" · "Fetch failed".
  • Facts: eligibility inputs from the offer snapshot (prime, condition, fulfilment) where present.
  • Steps:
    • Offer not eligible → Amazon: check condition, shipping template and fulfilment of the offer.
    • Not a featured merchant → Amazon: improve account metrics and sales history; it isn't fixable per listing.
    • ASIN not eligible → Amazon: Buy Box isn't offered for this ASIN; nothing to fix.
    • Fetch pending / failed / stale → Categra: no action; refreshes automatically.
  • Life cycle: non-price reasons → EXTERNAL / FIX_ON_AMAZON; fetch states → AWAITING_RECHECK "Awaiting refresh".

6.8 Buy Box lost / at risk Numbers missing

  • Chip suffix: "€24.90 › €22.50" (yours › target). The life-cycle chip stays (e.g. "Price above Buy Box").
  • Facts: your landed price, target and which kind (featured / expected / threshold), top 3 competing offers, last refresh.
  • Steps: Categra: Price tab › set ≤ {{target}} → publish → wait for the next buy-box refresh.
  • Life cycle: unchanged.

6.9 Listing blocked / warning Presenting missing on card

  • Chip suffix: "Compliance · 3", or "3 errors" when spread over several buckets.
  • Facts: per variant, attribute name + error text (capped by ISSUE_TICKET_EVIDENCE_MAX_ERROR_TEXTS, then "+n more").
  • Steps: Categra: Sync errors tab › fix the named attributes → publish → result arrives with the feed.
  • Life cycle: unchanged.

6.10 Not searchable (Amazon) / Not active (Shopify) Partial

  • Not searchable, chip suffix: "Buyable only" (Amazon status without DISCOVERABLE). Facts: status per variant; likely cause when the same product × marketplace has a LISTING_BLOCKER ticket. Steps: Categra: fix the blocking errors (link to that ticket) → publish; Amazon: if none, check Inventory › Fix your products.
  • Not active, chip suffix: "Draft" · "Archived" · "Unpublished". Steps: Categra: set the status to active on the channel tab → publish; or Shopify: Products › Status › Active and add to the Online Store sales channel.

6.11 Main image Presenting missing on card

  • Chip suffix: "Missing" · "WEBP".
  • Facts: current file type, allowed formats (ISSUE_TICKET_AMAZON_IMAGE_EXTENSIONS).
  • Steps: Categra: Media › upload a JPEG/PNG main image (Amazon: white background, ~1000 px+) → publish.

6.12 Stock sync Minor

  • Chip suffix: "12 vs 15" (mismatch) · "Push failing".
  • Facts: channel qty, Categra qty, failure error code + since.
  • Steps: mismatch → Categra: Stock tab › sync stock; push failing → check the error, then retry the sync.

6.13 Missing price / Out of stock / Low stock Fine

No change on the card: presenting stays null and the fix badge already explains. The ⓘ tooltip can still carry steps for consistency: "Price tab › set a price → publish", "Map a warehouse / add stock", "Raise stock above {{threshold}}".
