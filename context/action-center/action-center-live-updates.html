1. Core objective

Each account can have several members. Every member who has Action Center access should see ticket changes on their screen right away, whoever or whatever caused the change. That covers changes made by another member in Action Center and changes from system events (publishes, syncs, notifications). It applies on the Action Center page and on every other surface that shows the same tickets.

This document lists what can change a ticket and every surface that shows tickets. Each one is classified as Fully, Partially or Not implemented for live updates, with the evidence and a short note on the fix direction.

Scope (agreed 2026-11-23): Action Center board, dialog and insights drawer; product pages; Command Center; product list page; notification/sidebar badges. For permissions, this only checks that every permitted user receives the update. Over-broadcast and live role changes are not covered. Code analysis only, nothing run.

2. How live updates work today

2.1 End-to-end flow

Something changes a ticket
   ├─ system trigger (publish result, BS, webhook, notification, scope toggle, sweep …)
   │     └─ IssueTicketTriggerService.enqueue  → Redis pending set + debounced BullMQ job
   │           └─ IssueTicketEvaluationProcessor → evaluateScope()
   │                 └─ if created+reappeared+updated+cleared+moved > 0
   │                       └─ emit ISSUE_TICKETS_UPDATED { channelId, productIds | null } → account room
   ├─ publish started → IssueTicketPublishHookService moves tickets to Awaiting
   │     └─ emit ISSUE_TICKETS_UPDATED { channelId, productIds } → account room
   └─ user mutation (status / assignee / snooze / primary action) → DB write + audit event
         └─ (no socket emit) — only the caller's tab is updated from the HTTP response

Webapp: useIssueTicketRefresh (components/issue-tickets/use-issue-ticket-refresh.ts)
   listens to ISSUE_TICKETS_UPDATED (+ baseline / sync-status / FS sockets when a productId is given)
   → 1.5 s debounce → surface refetches its own data through the permission-scoped API

2.2 Socket rooms and delivery

  • When a client connects, it joins user:<id> and account:<id> (api/.../system/socket/socket.gateway.ts, socket.rooms.ts).
  • The webapp connects with query: { userId, accountId: currentAccountId }. Because currentAccountId is in the effect's dependencies, switching accounts reconnects and joins the new account room (webapp/.../_components/socket/socket-client.tsx:158).
  • Worker processes have no gateway. Their emits are relayed through JOB_STATUS_UPDATE → JobStatusRelayService, which handles target: 'account' (job-relay/job-status-relay.service.ts:42). So the evaluation processor's emit still reaches the browsers.
  • There is one ticket event: SOCKET_EVENTS.ISSUE_TICKETS_UPDATED (socket.config.ts:77). It is sent from exactly two places:
    • sync/queue/processors/issue-ticket-evaluation.processor.ts:49
    • system/operations/issue-tickets/issue-ticket-publish-hook.service.ts:125

2.3 Who receives it (permission check, receive side only)

Fully Every event goes to the whole account room. Every connected member of the account gets it, whatever their role or channel access. The payload holds only channelId and productIds, and each surface refetches through APIs that apply IssueTicketAccessService.resolveAccess (Action Center permission and allowed channels). So no permitted user is left out, and each user only sees ticket data they are allowed to see.

Side note: the board ignores the payload (productId: null matches everything). It refetches every lane on any ticket event in the account, even when it's filtered to another channel. That costs extra requests but is still correct.
